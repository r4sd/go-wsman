# ADR-0003: テストフィクスチャの作り方

> テーマ単位のファイル。決定が変わったら**末尾に追記**する(過去を書き換えない)。
> 詳しい運用は [README.md](README.md) を参照。

## 現在の決定

**fixture は録音する。手で書いたものは関所が弾く (ただし証明ではなく摩擦)。**
実機の応答は録音器が匿名化した XML として書き出し、印と本文の sha256 を持つものだけを
実機由来として扱う。合成データが要る場合のみ `testdata/synthetic/` に置き、
`derived-from:` でどの録音物から派生したかを書く。ソースに XML を直接書くことも禁止。

⚠️ 印も sha256 も自分で計算して貼れるので、**意図的な偽造は止まらない**。
止まるのは「それらしい XML を思いつきで書く」経路と「録音後に値を調整する」経路。

CIM は「成功を返して何もしない」ことがあるため、書き込みのテストは
**反転 → 確認 → 復元**の順で真の状態遷移を検証する
(方針として採用。既存テストの移行状況は下記「既存テストへの適用状況」を参照)。

## 2026-04〜: golden file は実機ダンプに限る

### 背景

CIM のレスポンス XML は入れ子が深く、名前空間の使われ方も一様でない。
テストを書くとき、**「たぶんこういう XML が返るはず」と手で書いた方が早い**。
実際そうしたことがあり、二度事故になった。

### 何が起きたか

**事故 1: 手書き XML の形式が実機と違っていた**

`hyperv/embedded_test.go` にその記録が残っている。

> 入力は 2026-07-04 に実機 Hyper-V ホストの GetVirtualHardDiskSettingData 出力から
> 採取した実形式に基づく (**旧テストは手書き WS-CIM ツリー形式で実機と乖離しており #89 の
> 遠因になった**)。

手書きの golden は「自分が想定した形式」を固定する。
実機が別の形式を返していても、テストは緑のまま通り続ける。

**事故 2: 実機に存在しない挙動を仕様として固定した**

2026-08-01、チェックポイント関連の PR で、手書き golden が
**実機には無い応答フィールドが返る前提**でテストを組んでいた。
CI は緑で、そのままマージされた。事後の批判的レビューで指摘され、修正した。

現在のテストにはこの教訓が明文化されている。

> 実機は非同期 (4096) のとき ResultingSnapshot を返さない (2026-08-01 実機確認)。
> **「SnapshotRef が取れること」を緑の条件にすると、実機に存在しない挙動を仕様として固定してしまう。**

同じ時期に、`VirtualSystemTypeSnapshotRealized` 定数の誤りも見つかっている(ADR-0002 参照)。
このときも**手書き golden が同じ誤りを含んでいたため、テストは実機と食い違ったまま緑だった**。

### 決定

- golden file は `{package}/testdata/` に置き、`{operation}_response_{対象}.xml` の形式で命名する
  (対象は CIM クラス名か、`invoke` の場合はメソッド名。応答のバリアントを区別する接尾辞を足してよい)
- **実機からダンプしたものだけを使う。** ファイル先頭に採取日と対象メソッドを
  `<!-- recorded: YYYY-MM-DD host=<hyperv-host> method=... -->` の形で残す
- 実機で確認できない挙動を「こうなるはず」としてテストの緑の条件にしない
- 実機の挙動が期待と違うなら、**テストではなく期待の方を直す**。差分は Issue で追跡する

### なぜ規約だけでは足りなかったか

手書き golden の危険は 2026-04 の時点で分かっていたが、それでも 2026-08-01 に再発した。
原因は**レビューを飛ばしたこと**で、`CLAUDE.md` に次の一文が足された。

> provider を伴わない go-wsman 単独の PR も DoD ⑥(Fable 批判的レビュー)の対象。PR 作成と
> 同時にバックグラウンドで起動し CI と並走させ、**CI green だけでマージしない**。(中略)
> golden 手書きは本リポジトリ特有の事故源なので、単独 PR ほど効く。

**golden file が間違っていると CI は緑になる。** だから CI は防波堤にならず、
人間(またはレビュアー)が実機と突き合わせるしかない。これがこのリポジトリ特有の事情。

## 2026-07〜: 「黙殺」を検出できるテストにする

### 背景

CIM のメソッド呼び出しには、**受理して成功を返すが、実際には何も変わらない**ケースがある。

- `ModifySystemSettings` が Job を成功で返すのに、設定が元のまま
- ゼロ値を渡すと「指定なし」と解釈され、書き込みが静かに落ちる
- 大文字小文字の違いで照合に失敗し、差分なしと判定されて書き込みがスキップされる

これらは例外を投げない。**ログにも何も出ない。** 素朴なテストでは緑になる。

### 何が問題だったか

当初、書き込みのテストは **no-op 書き戻し**(読んだ値をそのまま書く)で済ませていた。
これでは不十分だと批判的レビューで指摘された。テストのコメントに記録が残っている。

> no-op 書き戻し (before と同じ値を書く) だけでは「**Set が受理されたが実はサイレントに無視された**」
> ケースを区別できない (Fable レビュー指摘、PR#112)。

実際に、ゼロ値が黙って捨てられる不具合が別途見つかっている
(`hyperv/integration.go` のコメント「processor の bool フィールドで発覚したゼロ値ダウングレード黙殺」)。

### 決定

**書き込みの統合テストは値を反転させ、真の状態遷移を確認する。**

```
① 現在値を保存
② 反転して Set
③ Get で反転後の値を確認   ← ここが本体。黙殺ならここで落ちる
④ 元の値へ Set で復元
⑤ Get で復元を確認
```

復元は `defer` で保証し、途中でアサーションが失敗しても実機の状態を変えたまま終わらせない。

さらに、実機を壊さないよう**書き込み系は二重の環境変数ゲート**を要求する。

| 環境変数 | 役割 |
|---|---|
| `HYPERV_TEST_ALLOW_MUTATION` | 書き込みを許可する。未設定なら skip(既定では実機に書き込まない) |
| `HYPERV_TEST_TARGET_VM_NAME` | 対象 VM の表示名。環境ごとに異なるのでハードコードしない |

読み取り系は `WSMAN_ENDPOINT` / `WSMAN_USERNAME` / `WSMAN_PASSWORD` が未設定なら skip する。
統合テストは `//go:build integration` タグで分離してあり、通常の `go test ./...` では動かない。

### 根拠

このプロジェクトで見つかったバグの多くは、クラッシュではなく**静かな不作為**だった。
つまり脅威モデルは「落ちること」ではなく「**落ちずに間違っていること**」であり、
テストはそれを検出できる形でなければ意味がない。

### 既存テストへの適用状況(2026-08-27)

**この方針は決めたが、既存の書き込みテストがすべて従っているわけではない。**

反転パターンで書かれているのは `TestIntegration_SetIntegrationServiceEnabled` のみ。
たとえば `TestIntegration_SetMemorySettings` は、読んだ値をそのまま書き戻して
Job が返ったことだけを確認する **no-op 書き戻しのまま**で、本節が「不十分」と判定した形に該当する。

新しい書き込み経路には反転パターンを適用し、既存分は気付いたときに移す。
残作業は #131 で追跡する。

### 見直しの条件

- [ ] 実機を常時使える CI 環境が用意できた → golden file への依存を減らし統合テストを自動化する
- [ ] 反転テストが実機に副作用を残す事故が起きた → ゲートの粒度を見直す

## 2026-09-14: 規約をやめ、手書きを置けなくする (#157)

### 背景

2026-04 の決定「golden は実機ダンプに限る」は**規約として一度も守られなかった**。

- 事故は 7 回に増えた (#124 / #126 / #136 / #137 / #143 / provider #145 / PR #152)
- 本 ADR が要求する `recorded:` ヘッダは golden 70 件中 **3 件**にしか無かった
- **5 回目は「4 回繰り返している」と CLAUDE.md に書いた同じセッションが数時間後に
  起こした**。警告が直前のコンテキストにある状態で再発している
- 録音物を後から手直しした実例もある (`invoke_response_get_vhd.xml` のヘッダに
  「値は代表値に調整 (アサーションに合わせた)」)

### 何が間違っていたか

「実機から採取した」と書いてあるかを見る設計だった。**主張の真偽は機械検証できない。**
CI が判定できるのは証跡の有無だけ。

もう一つ、**正しい道が間違った道より高かった**。匿名化と golden 化が手作業で、
「それらしい XML を 6 行書く」方が安かった。禁止を増やしても、安い方へ流れる。

### 決定

信頼の向きを反転させる。

1. **録音経路を用意して、そちらを安くする。** `WSMAN_RECORD_DIR` を設定して統合テストを
   回すだけで、応答が 1 つずつ匿名化済みの XML として貯まる。使うものをコピーするだけ。
   匿名化は自動 (伏せる名前は実機から自分で集める)。保存後に読み返して検証し、
   残っていたら落とす。
2. **印と sha256 を持たない fixture を拒否する。** 合成は `testdata/synthetic/` +
   `derived-from:` のみで、**派生元が録音物であること**まで確かめる
   (legacy を指せると、印を回避する最安の抜け道が synthetic/ に移るだけになる)。
3. **ソース中の生 XML も禁止する。** testdata に関所があってもそこで迂回できる。
   既存ファイルは**出現数まで固定**する — 「既存テストに新しいケースを足して、そこに
   生 XML を書く」が今後の最有力経路で、ファイル単位の許可だけでは素通りになるため。

既存分 (golden / 生 XML を含むソース) は許容リストに載せて落とさない。
棚卸しを独立した作業として積まない。**触ったときに録音し直してリストから外す**。
消した fixture のエントリが残っていても落ちる (幽霊を残さず、リストが実際に縮むように)。

### go-vcr を採用して外した

録音・再生の OSS として go-vcr v4 を一度入れた。録音は問題なく動いたが、**再生が噛み合わなかった**。
本リポジトリの単体テストは `ParsePullResponse(loadGolden(...))` 型で HTTP 会話の再生を必要とせず、
再生を使おうとすると WS-Man 固有の照合 (全リクエストが同じ URL への POST、MessageID は毎回変わる、
録音時に URL は匿名化される) を自作することになった。「肩に乗ったつもりで肩の上で別の車輪を作る」
状態だったので、応答の採取だけに絞り依存を外した。会話の再生が要る形のテストが出てきたら再検討する。

### この決定で守れないこと

「fixture が本物か」と「**テストが実機挙動を正しく主張しているか**」は別問題。
後者は録音でも守れない (#126 は golden 自体は正しく、テストの緑条件が実機に無い
挙動だった)。これを拾えるのは別コンテキストからの批判的レビューだけ。
