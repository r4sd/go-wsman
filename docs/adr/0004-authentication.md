## 2026-04: NTLM と証明書認証を選ぶ

### 背景

WinRM が受け付ける認証方式は Basic / NTLM / Kerberos / CredSSP / 証明書がある。
どれを実装するかを決める必要があった。

### 選択肢と評価

| 方式 | 前提 | 判断 |
|---|---|---|
| NTLM | ワークグループ(ドメイン不要) | ✅ 採用 |
| TLS クライアント証明書 | 証明書の配布が必要 | ✅ 採用 |
| Basic | 平文。HTTPS 必須でも推奨されない | ❌ 単独では非対応 |
| Kerberos | Active Directory ドメインが要る | ⏸ 保留(Issue #8) |
| CredSSP | 資格情報の委譲。攻撃面が広い | ❌ 却下 |

### 決定

NTLM を第一級の方式として実装する(`wsman.WithNTLM` / `wsman.WithNTLMAuth`)。
NTLM ハンドシェイクは `github.com/Azure/go-ntlmssp` に委ねる。

TLS クライアント証明書も併せて対応する(`WithCertificate` / `WithCertificateConfig` / `WithCACert`)。

**Basic 認証は独立したオプションとして提供しない。** NTLM ハンドシェイクの内部で
資格情報を運ぶ手段としてのみ使う。

### 根拠

**Kerberos を保留にしたのは、それを使える環境の構築コストが高いため。**
Kerberos には Active Directory ドメイン(または対応する KDC)が要る。
ワークグループ構成の Hyper-V ホストが対象なら NTLM で足りる。

ドメイン環境で使いたい要望は Issue #8 で追跡している。
実装するなら `github.com/jcmturner/gokrb5` が候補になる(**未検証**)。

**CredSSP を却下したのは、資格情報をリモートホストへ委譲する方式だから。**
リモート先が侵害されていた場合の被害が大きく、この用途では必要性がない。

## 2026-07-27: NTLM の並行実行で 401 になる問題に接続プールで対処

### 背景

Terraform から使うと、既定の並列度(`parallelism=10`)で複数リソースが同時に読まれる。
このとき **7 件の並行 `GetVhd` がすべて 401 で失敗**した。`parallelism=1` なら成功する。

### 原因

NTLM は**コネクション単位でハンドシェイク状態を持つ**プロトコルで、
negotiate → challenge → authenticate の 3 ステップが同一 TCP コネクション上で完結する必要がある。

Go の `*http.Transport` はコネクションプールを共有するため、
ある goroutine のハンドシェイク途中に別の goroutine のリクエストが同じコネクションへ割り込み、
**サーバー側の NTLM 状態機械が混乱して 401 を返す**。

これはライブラリの実装ミスではなく、**NTLM のステートフルさと HTTP コネクション再利用の相性問題**。

### 選択肢と評価

| 案 | 内容 | 判断 |
|---|---|---|
| A: 独立したプールを N 個持つ | 各スロットが専用の `*http.Transport` を持つ | ✅ 採用 |
| B: 全体を 1 本のミューテックスで直列化 | 単純だが並列性がゼロになる | ❌ 却下: 遅すぎる |
| C: 呼び出し側に `parallelism=1` を強制 | ライブラリ側は何もしない | ❌ 却下: 利用者に押し付ける |
| D: `DisableKeepAlives` で毎回新規接続 | 毎リクエストでハンドシェイクが走る | ❌ 却下: 往復が増える |

### 決定

A を採用。`wsman/pool.go` の `pooledTransport` が N 個の完全に独立した `HTTPTransport`
(それぞれ別の `*http.Client` とコネクションプールを持つ)にリクエストを振り分ける。

**1 スロットは同時に 1 リクエストしか扱わない**(チャネルで排他)。
これにより割り込みが構造的に起こりえなくなる。全スロットが埋まっていれば `ctx` が完了するまで待つ。

### 根拠

対症療法(B・C・D)ではなく、**割り込みが起きえない構造にする**方を選んだ。
B と D は性能を犠牲にし、C は同じ問題を利用者に転嫁するだけで、いずれも原因を消していない。

### 見直しの条件

- [ ] ドメイン環境で使いたくなった → Issue #8 の Kerberos 対応に着手する
- [ ] 適切なプールサイズが環境によって変わることが分かった → 既定値の調整、または自動調整を検討する
